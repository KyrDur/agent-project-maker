# AI 产品经理项目材料与评测修订依据

研究日期：2026-10-06。此次完成外部研究和现有实验核查，尚未修改产品代码或重新评分。

## 外部依据

1. [牛客：面试官视角聊聊，怎么准备 AI 大模型产品面试？](https://ac.nowcoder.com/discuss/1607778?type=0)：作者自述为业务面试官；强调项目背景、具体参与、业务指标和复盘，追问评测数据从哪里来。属于社区经验，身份与招聘结果未独立核验。
2. [牛客：面试官视角聊聊，怎么讲清楚自己做的 AI 项目](https://www.nowcoder.com/discuss/846095175859306496)：按业务逻辑、实现细节、数据结果、迭代思考组织项目介绍。文中示范数字不能移植到本项目。
3. [个人 AI 产品经理作品集示例](https://limingyuan.top/)：把具体场景、承担的工作和结果连接起来。经历与业绩为作者自述，只参考表达结构，不作为评测标准或已验证业绩。
4. [Harvard：Creating a Strong Resume](https://careerservices.fas.harvard.edu/resources/create-a-strong-resume/)：简历应简洁，围绕目标岗位突出经验与能力。
5. [Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：区分运行轨迹与最终结果，优先采用确定性检查；模型判断需要校准，重复试验用于观察稳定性。
6. [τ-bench 研究论文](https://proceedings.iclr.cc/paper_files/paper/2025/hash/1b126cc38b8638e07bef37e7b2bb72bf-Abstract-Conference.html)：零售客服模拟任务通过最终数据库状态对照目标状态验证操作结果，并考察多次试验的可靠性。
7. [Ragas：Faithfulness](https://docs.ragas.io/en/latest/concepts/metrics/available_metrics/faithfulness/) 与 [Context Recall](https://github.com/vibrantlabsai/ragas/blob/main/docs/concepts/metrics/available_metrics/context_recall.md)：事实支持率需要逐项事实证据；召回评测需要参考信息。不能把任意主观分数重命名为这些指标。
8. [Ragas：Align an LLM as a Judge](https://docs.ragas.io/en/latest/howtos/applications/align-llm-as-judge/)：用参考标注检查裁判误判，修订判据后重新验证。普通用户仍使用自动评分；裁判校准由产品开发验收承担，不恢复强制人工评分或用例抽查。

## 本项目核查结果

现有简历有 26 条 bullet，混杂全部指标、版本和决策记录，缺少清晰的项目背景、个人行动与案例。报告过长，引用部分被脱敏为不可定位的字符串；简历、面试和原始证据需要分层呈现。

当前是模型 B 生成、冻结的 20 条模拟用例，不是真实客户日志、行业标准测试集或生产 A/B 实验。V1 已完成基线为 12/20，V2 为 11/20，V3 为 13/20；旧口径结果需保留。V2→V3 修复 5 条、新增失败 3 条。不能据此声称生产问题解决率提高、节省人工成本或具有统计显著性。

旧规则把格式与事实、业务结果并列为通过门槛。物流查询正确但缺少共情或满意度邀请也会失败，这只能称该项目约定的格式不满足，不能直接等同业务失败。

裁判还有需要验证的一致性问题：价保 V3 的事实评分理由承认一处无依据延伸，却给 0.9；冻结判据明确写一处扣 50%。商品 V3 增加“平铺测量”而工具未提供该信息，裁判仍判事实满分。需要保留原判定，同时标记待复核；不能直接把模型裁判分数当作事实。

工具正确性当前案例的程序检查主要是必需/禁止工具；并未验证所有参数语义。例如商品用例的 tool_arguments 为空。材料不能把“调用了 query_product”扩写为“工具名、参数与返回结果均正确”。

## 修订后的材料结构

### 简历项目经历

一项项目，标题明确“模拟实践”，约 3 条短段落：

- 需求与取舍：目标人群、核心任务、为何选择这些工具/文本指南、本人确认了什么。
- 评测与定位：自动生成测试集的来源、规模、覆盖场景、程序/裁判各检查什么，聚焦一两个具体问题。
- 迭代与结果：本人选择的改动及理由、同口径前后结果、退步与边界。

STAR 的情境和任务可以压缩进背景，简历重点写行动和结果；完整四段叙述放到面试卡。系统生成的测试集不能写成用户独立设计；本次 V3 为 Codex 演示审批，不能写成用户本人主导。

当前能确认的保守草稿：

> 电商客服 Agent｜模拟项目实践
>
> 确认订单、物流、商品和售后咨询需求，选择查询接口与客服文本指南，在模拟环境中验证事实回答与转人工边界。
>
> 使用系统生成的 20 条固定用例开展自动评测，结合工具调用记录与裁判依据检查工具选择、回答事实及异常处理。
>
> 选择“意图—工具对照与订单号先核验”方案生成 V2；该轮通过数由 12/20 降至 11/20，回归记录显示修复 4 条、新增失败 5 条。

这只是已确认贡献的表达草稿。用户尚未亲自解释的 V3 案例不包装为个人成果；通过学习和实际决策后再按真实记录增补。

### 每个项目至少两张案例卡

卡片必须有：用户原话、模拟初始数据、实际工具参数/返回、具体错误、成功条件、检查方法、改动、前后表现、剩余问题和版本/用例引用。首页用自然语言日志呈现，原始 JSON 放到可选详情。

## 本次可用于学习的两个实际案例

### 案例 1：商品咨询中的无依据补充

- 场景：用户问“这款纯棉短袖 M码的材质是什么？M码大概多大？”
- 数据：query_product 返回材质 100% 棉、衣长 68cm、胸围 104cm、库存 120、价格 89 元，没有测量方法、测量误差或库存充足的定义。
- V2：正确返回核心数值，但补充“亲肤透气”“1–3cm 误差”“库存充足”。旧裁判事实评分 0/1，整体失败。
- 改动：V3 指令要求事实结论来自实际返回，禁止把库存数量扩写为充足。
- V3：删除上述补充，旧裁判评分 1/1，整体通过；仍新增“平铺测量”，本次核查发现此项未有来源。
- 应检查：必需事实是否回答正确；每条新增事实是否有来源；建议与事实是否分开。逐条列支持/不支持，稳定字段用程序比对，语义事实由裁判引用来源判断。
- 可讲结论：修订减少了无依据补充，但旧裁判漏检，不能称幻觉已消除。两个评分是现有旧裁判记录，不是新定义的事实支持率。
- 引用：experiment-3/case-4 与 experiment-4/case-4。

### 案例 2：知识库为空时虚构转人工成功

- 场景：用户问“你们支持价格保护吗？怎么申请？”
- 数据：search_faq 返回空；转人工调用报 evaluation_mock_missing，未生成工单。该错误是测试场景缺少对应模拟返回，不能写成真实服务故障或有意故障注入。
- V2：说“我已为您登记转接人工客服”，没有成功结果支持；事实评分 0.5/1，整体失败。
- V3：说“本次转接也未成功、未生成工单”，旧裁判整体通过，但转人工仍失败，还提出无依据的“提供订单号核实”。
- 应检查：不编造价保规则；声明成功必须有工单/状态支持；转接失败应如实说明；失败后的建议必须可执行。
- 需要分开统计：失败如实告知、业务转接成功、政策问题解决。此例前者改善，后两者没有完成。
- 环境修补：为正常转人工提供完整模拟数据；另外建明确注入失败的场景。不能把场景缺项当成 Agent 的恢复能力测试。
- 引用：experiment-3/case-16 与 experiment-4/case-16。

## 评测修订方案

以下是结合外部方法与当前证据的项目适配方案，不是照抄的行业通用阈值。

1. 先定义任务成功、关键业务约束、可接受替代路径；评价业务结果与表达质量分开。无依据的关键事实、越权操作、虚构成功不能被语气高分抵消。格式何时构成硬限制应由实际业务需求明确。
2. 模型 B 生成每例输入、初始状态、参考事实、允许的最终状态与判断依据；系统验证工具返回完整、参考解可通过、正常/异常场景不矛盾。已实现校验继续复用，仅补缺口。
3. 程序检查参数标识、状态变化、次数、明确长度等可计算约束；模型 C 对事实和内容质量逐条提供证据。复杂参数语义不声称仅靠工具名检查已覆盖。
4. 事实支持率按有证据的事实条数/被检查事实条数定义；转人工成功率只统计需要转人工的适用用例；恢复成功率只统计明确故障且允许恢复的场景。分母、覆盖数、不可评估项必须显示。
5. Hit@K、Recall@K、MRR 仅在确有检索结果及相关性参考标注时启用。当前固定 FAQ 返回只验证 Agent 如何使用给定结果，不证明检索算法效果。
6. 开发侧用标注过的正反样例校准 C，检查误判、规则和分数一致性；配置同一模型担任多个角色也要明示。未校准不称可信行业标准。
7. 保留 20 条作为起步回归集，额外留出未用于优化的验证用例；重复运行观察波动。没有重复实验则只报告本轮样本结果。
8. 改变评分口径开启新范围，必要时对 V1/V2/V3 同口径重新运行；不改写原来的 60%/55%/65%。

## 实施顺序与验收

先修测试场景与裁判校验，再重构材料生成。保留现有冻结、版本、日志和导出机制，不重新搭一套。

验收关注：每条简历陈述能对应真实个人记录；至少两个有内容的案例卡；每个数字有分母和引用；不能把失败告知写成业务成功；退步保留；案例正文和日志一致；预览与导出一致。没有足够证据的项目应明确缺少哪些案例或数据，不自动编故事。
