# Agent Project Maker：可信评测、可解释案例与 AI 产品经理材料完整修订大纲

日期：2026-10-06。状态：修改方案，尚未执行本方案的代码变更。

## 目标与质量标准

用户用个人 Key 创建通用 Agent，在纯模拟环境中试用；系统自动评测、展示可核查的失败证据；用户确认改动并观察 V1/V2/V3 回归；最终取得简洁的中文 AI 产品经理项目经历和至少两个能展开讲的实际案例。

本轮质量标准是：成功条件清楚、测试环境有效、评分可复核、每个结论可追溯、个人贡献如实、预览与导出一致。没有依据的地方明确缺失，不填成好看的结论。项目成绩高低不是完成门槛。

继续保持：模型 A 生成/执行/修改，B 设计测试，C 裁判/分析；三角色个人配置可主动复用同一模型或凭据，必须显示实际模型，不声称角色独立就证明判断可靠。普通用户不手工打分、不强制抽查用例。V3 可选，基于 V2 继续；纯模拟，不新增真实业务、脚本型 Skill 或 MCP 接入。

## 现有能力处置

保留并补验：创建失败重试、需求传递、文本 Skill 冻结、独立模拟聊天、冻结用例、状态操作与故障配置、版本/回归/幂等、结构化评分与证据引用验证、材料及 ZIP 导出。

重点扩展 agent_project_semantic/rubric/evaluation/mock_tools/portfolio/materials 及现有项目页面，沿用 Router → Service → Model；不重新搭建平行流程。增加存储字段时通过 Alembic 迁移并同步前端类型。

## 一、把“成功”定义成需求契约

1. 将需求拆成可引用的任务目标、必要输入、成功结果、关键禁止行为、业务依赖、质量偏好、已确认模拟假设。
2. 每个判据保存来源字段、原文、适用条件、验证方法、通过/部分/失败锚点，以及是否决定业务任务通过。
3. 任务判定由核心成功条件和明确关键约束决定；表达质量独立显示。共情、满意度邀请不能自动成为所有任务的失败门槛；用户明确指定的硬格式/长度仍要检查。
4. 不强制所有项目套同样 3–5 个指标，也不强制三个固定池指标；只显示有实际适用检查的指标。阈值不是“行业通用 75 分”，必须解释规则依据并冻结。
5. 未知规则由用户补充或确认模拟假设，不由 B/C 自行补成事实。保留系统提出与用户确认的来源区别。
6. 能力分类根据明确能力定义，不以存在文本 Skill 就判断有知识检索，不以指令里的关键词推断真实检索架构。

验收：无工具/无 Skill 项目正常执行；没有适用工具检查时不显示工具满分；回答正确但遗漏非关键寒暄只影响表达质量；关键业务违规不能被其他高分抵消。

## 二、模型 B 生成的测试必须先证明可执行

保留 20 条正式回归集。每例补齐任务类型、初始数据、实际输入/历史上下文、必需事实、允许的成功结果、明确业务约束、适用指标、参考轨迹或参考答案，以及模拟响应定义。

自动预检：

- 工具名、输入/输出约定与版本匹配，必要参数有来源，模拟数据能够匹配实际输入。
- 正常和可接受替代路径具备完整响应；故障场景显式声明失败方式和可恢复条件。
- 检查涉及最终状态时，环境确实能写入并读取该状态。
- 参考结果通过程序判据；文本判据由 C 检查与需求一致性，但这不替代后续裁判校准。
- 正/反/信息不足/边界/异常/多诉求有适当覆盖，重复题与自相矛盾的题不能冒充多样性。
- 对“应调用”和“不应调用”、“应转人工”和“不应转人工”同时覆盖，避免单向优化。

缺少模拟返回是环境缺陷，不能默认返回 null 后算业务完成，也不能伪装成主动故障注入。非法/缺项场景阻止新测试集冻结，保留错误与重试入口；运行中遇到未覆盖路径时保存已产生证据并标记环境错误。历史记录不重写。

参考轨迹只是验证环境能完成任务，不用于强制 Agent 逐步照抄。

验收：正常查询可命中，写操作产生状态，主动失败可按约恢复；环境缺项不能显示成模型成功；用例相互隔离；普通聊天默认场景加载完整且能恢复最近选择。

## 三、程序检查与 C 裁判分工明确

程序负责可确定检查：标识/参数来源、明确参数规则、允许或禁止操作、必要业务顺序、最终状态、次数/重试、JSON 结构、明确字符限制。

模型 C 负责语义检查：核心诉求是否满足、信息是否遗漏、回答事实是否有依据、模糊需求是否恰当澄清、边界说明是否恰当、表达质量。复杂参数语义不能只靠工具名检查就宣称已验证。

关键区分：

- 调用了操作不等于操作成功；操作成功不等于用户整个问题解决。
- 回答如实承认失败可以满足异常场景的要求，但不能记成正常业务操作成功。
- 禁止只因顺序不同而拒绝有效方案；仅对明确必要业务依赖限制顺序。
- 工具返回字段与需要检查的事实逐条关联，区分事实、建议、条件表达及无依据断言。
- C 不读取 Agent 未见的参考数据来证明回答有依据；判题目标和 Agent 实际可见来源分别标记用途。
- 引用必须存在；证据存在不自动证明语义判断正确。裁判缺判项、引用错误或不足以判断时是评测错误/不可判断，不默认通过。

评分计算由程序根据逐项判定完成，C 不自由生成总分。保留旧 rubric 读取，新规则另开范围。

验收反例：商品字段正确但新增测量方法应识别；转人工调用失败后声称已登记应识别；单纯没有寒暄不能被当作未查询到物流；将指令/提示注入写进返回内容不得改变裁判规则。

## 四、开发侧验证裁判本身

建立经开发侧审定的正反样例，覆盖关键数值错误、额外事实、政策无依据、虚假成功、正确拒绝、合理替代路径、仅表达不佳、环境故障、信息不足、恶意输出干扰裁判。

保存每例参考标签与理由、标签制定者/来源、C 判定、误判类型和引用。实际专家参与才称专家标注，不把模型生成标签称为人工标准。

报告误放行、误拒绝、关键违规漏判、判据与等级一致性；用独立样例复验修订，不在同一批数据上调整并宣称泛化有效。人工校准是开发验收任务，普通用户仍自动评分。

现有两个旧实验疑点作为回归样例：V3“平铺测量”未有来源却事实满分；价保有一处无依据延伸却给 0.9，与旧扣分规则不一致。原判定、复核记录和后续新实验必须分开保留。

校准不足时页面显示未验证状态，材料不得宣称“行业标准评测”或裁判已经可靠。

## 五、统计回答清楚分子、分母与范围

结果分开显示任务通过、任务失败、执行错误、环境错误、裁判错误。环境错误可作为执行错误子类，但同一个错误不能重复计数。

| 数据 | 定义与限制 |
|---|---|
| 全部用例通过率 | 通过数 / 冻结计划的全部用例数；错误不移出分母 |
| 有效评分任务通过率 | 通过数 / 已执行且可有效评分的用例数；同时展示完整分母和错误数 |
| 业务操作成功率 | 成功达到操作目标的用例 / 适用该操作的用例；不是工具调用次数成功率 |
| 关键违规率 | 发生关键违规的有效评分用例 / 适用并已评分的用例 |
| 事实支持率 | 有来源支持的事实条数 / 被检查事实条数；展示不支持与无法判断的条目 |
| 恢复成功率 | 完成允许恢复目标的场景 / 明确注入可恢复故障的适用场景 |
| 表达质量 | 冻结锚点下的评分，标注覆盖数；不冒充业务成功率 |

未评分/N/A 不能当 0 或 1 混入均值；未完成实验不能显示完整成绩。多用例事实汇总明确采用事实条数汇总还是逐例均值，不能混用。

Hit@K、Recall@K、MRR 仅在确有检索结果、排名和参考相关性标注时启用；固定 FAQ 返回只证明 Agent 使用这些返回的表现。

时延、调用次数、Token 和成本只基于已记录数据；缺失显示不可用，缺价格信息不估造费用。统一各页面与导出的精度和舍入规则。

## 六、让 V1/V2/V3 比较有约束、有边界

冻结需求、接口/Skill 正文、回归用例/数据、判据、A/B/C 配置、调用参数及执行协议。候选只在已允许范围改指令、文本 Skill、工具说明与运行配置；不能修改判题口径获得高分。

每轮保留来源运行、C 分析、A 的 2–3 个方案、证据、预览差异、用户理由与幂等键。V3 固定基于 V2，退步也不自动改用最佳版本；无可验证改进不制造版本。

除了固定 20 条回归集，支持单独冻结的验证集，在优化期间不向 A 提供其具体内容/结果。生成依据仍为同一确认需求，由 B 设计、系统验证。用户完成一轮迭代后可查看验证证据；如果再据这些证据优化，此集明确变为已使用数据，不能继续声称未见验证。

支持每版每例重复试验；强化验证建议重复 3 次，次数属于本项目运行配置，不是行业统一门槛。运行前展示新增调用量与可用预算信息，用户可选择；单次结果标注稳定性尚未验证。重复结果分别保留，不能挑最好一次作为版本代表。

展示相邻与累计变化、修复/新增失败、分场景表现、样本数量与波动。最佳版本按同范围预先固定口径选取，同分保留较早版本；改变口径的运行不共同排名，不自动替换用户正在运行的 Agent。

旧 60%→55%→65% 原样保留并提示待复核事项。新规则需要对三个快照在新范围同口径重跑，不能把新版成绩和旧版成绩直接对比。

## 七、建立统一证据与陈述来源

统一数据：需求及确认 → 版本 → 运行/试验 → 用例 → 操作事件/状态 → 判据/裁判 → 改动与决策 → 案例 → 材料。

每条材料陈述保存引用、类型（事实/判断/目标）、来源、作者与验证状态；系统生成、用户亲写、用户确认、Codex 演示分别记录。用户理由原文不改写为更强的个人贡献。

展示使用“V3 / 第1次试验 / 商品尺码咨询”与事件编号，底层映射稳定 ID。导出使用一致的可公开别名；脱敏隐藏个人信息而不破坏引用，不能把引用全部替换成 [redacted]。

所有成果由同一冻结证据版本生成。材料生成后出现新运行、修订或补充时显示过期，需要重新生成；用户润色不得悄悄改变指标、数据来源或贡献事实。

## 八、每个项目生成两个实际案例，而非两段模板

优先选不同能力/根因，覆盖有实质改动的案例与暴露边界的案例。没有失败时选薄弱指标或已实际执行的边界场景；不足两个真实案例则标记材料待补充，不编造。

每张卡提供：

1. 用户原话和业务背景。
2. 本人实际任务与系统承担的工作。
3. 可读时间线：模型调用、工具参数、返回事实、状态变化、最终回答、终止原因。
4. 预期结果、判据来源、检查方法及具体判定。
5. 错误定位、候选改动与为什么这样选。
6. 同一用例的前后证据、整体回归及新增失败。
7. 未解决问题和实验边界。
8. 简短 STAR 讲述与证据链接。

本次优先两例：商品事实无依据补充；FAQ 空结果后的转人工虚假成功。后者的准确结论是失败告知改善，而业务转接仍未成功，并存在模拟场景缺项。

用户可以改选案例、查看判据和记录自己的理解，系统不代写“本人已理解”。练习讲解是可选学习功能，不是人工评分入口。

## 九、重写简历、面试与报告

简历项目经历：项目名/模拟实践标签、一句目标与范围、3–4 条紧凑经历。每条连接本人行动、方案取舍与结果，不列所有指标或运行 UUID。未验证的成本节约/客户满意度/生产部署不写成成果；退步照实表达诊断与决策，不包装为提升。

STAR 完整展开在案例卡和面试材料。系统可以把实际行动表达得更清楚，但不能改变谁做了测试设计、谁选择了优化。本次 V3 演示审批不写成用户本人主导。

面试材料：一分钟项目介绍、两张 2–3 分钟案例卡、针对证据的追问。重点问题包括数据来源、核心成功定义、程序/C 的分工、参数检查、事实支持、为何选该修改、退步原因、测试边界与如果重做。回答要点附引用、不能声称的内容及缺失数据。

报告按“结论 → 方法 → 两个案例 → 版本数据 → 局限”组织，完整证据作为附录；替换大段 Python/JSON 字典堆叠。ZIP 包含一致的报告、简历项目经历、面试案例、评测规范、版本/差异及脱敏原始证据。

验收：中文自然可读；不使用未经解释的英文指标/散列标签；每个结果有分母、范围与引用；无未经授权的个人经历，预览与导出完全一致。

## 十、用户路径只突出当前该做什么

五个主要步骤：确认需求与能力 → 聊天试用 → 查看自动评测 → 确认优化并自动回归 → 查看案例与成果。

- 当前阶段/正在运行/完成/失败/待重试清楚展示，已运行时不误写尚未运行。
- 下一步只有一个主要动作；生成建议失败显示对应 A/C/场景/校验原因和恢复入口，保留已有内容。
- 三版标签使用 V1 基线、V2 第1轮、V3 第2轮，运行摘要放在标签内，ID 放在详情。
- 成绩页先呈现业务结果与关键风险，再表达质量，最后技术记录。
- 日志默认自然语言，不要求读 JSON，也不伪造模型内部思维过程。
- 决策理由说明“你确认哪个取舍，为什么”，附适配当前任务的例子；例子不自动冒充用户本人理由。
- 聊天场景选择、版本与会话刷新恢复，聊天状态与正式实验隔离。
- 分开标记实验完成、分析/案例就绪、材料已生成/待确认；完成不代表生产可用、也不要求达到最低分或强制生成 V3。

## 执行批次

P0：成功契约/任务与表达分离 → 场景预检及缺项错误 → 程序/C 判定一致性与裁判反例。

P1：统一统计与重复运行/验证范围 → 证据别名与来源 → 两个案例卡 → 简历/面试/报告重写。

P2：流程导航与恢复 → 四类完整验收 → README、验收记录、PR。各批次就地完善现有实现；已完成的 P0 UI/评分代码补验而不是重复建设。

## 最终验收矩阵

| 验收项 | 必须能证明 |
|---|---|
| 成功规则 | 指标来自需求，任务与表达分开，关键违规不被均分掩盖 |
| 模拟环境 | 正常/异常/替代路径均可执行，缺项明确失败，参考解能通过 |
| 自动裁判 | 预先审定反例可检出，引用真实，等级/算分一致，校准范围披露 |
| 统计 | 分母/覆盖/错误/未完成一致，无挑最好一次或隐藏新增失败 |
| 多轮 | 两轮审批、幂等、V3 基于 V2、不同口径隔离、无需改进可结束 |
| 案例 | 至少两个真实场景，有输入/返回/错误/改动/判据/数据/剩余问题 |
| 个人贡献 | 用户与系统及演示操作来源明确，没有编造职责或收益 |
| 材料 | 简历简洁可读，面试追问有答案依据，预览/导出数字引用一致 |
| 四类项目 | 写作、客服、知识问答、纯对话，含无工具/无 Skill 和失败/退步路径 |
| 工程 | 隔离 PostgreSQL 迁移/历史兼容，相关 pytest/Vitest/Playwright、类型、构建、国际化、无障碍与设计系统检查 |

固定响应验证与实际模型验收分别交付。真实运行使用用户页面中的有效个人配置，不以测试模型代替；预检失败先修复，不继续制造好看的成绩。

本方案不承诺任意生成的领域测试集具有专家级效度。缺少领域审定、重复试验或真实业务数据时如实披露，产品通过的只是相应已验证范围。
