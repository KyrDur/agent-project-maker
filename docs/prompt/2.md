## 📋 Tool Guidelines 编写指南

### 基本结构

每个工具都必须包含以下**3 个必需元素**:

```markdown
### `{工具名}`
- Purpose: [功能说明]
- When: [何时使用]
- Caution: [注意事项]
```

---

## 🎯 各元素编写方法

### 1️⃣ **Purpose（目的/功能）**

简明说明**这是做什么的工具**

#### ✅ 好的示例
```
- Purpose: 在互联网上搜索最新信息
- Purpose: 分析用户问题并进行澄清
- Purpose: 读取并处理文件内容
```

#### ❌ 不好的示例
```
- Purpose: 工具（过于模糊）
- Purpose: 可以做很多事情（不够具体）
```

#### 💡 编写技巧
- 用 1-2 句话简洁说明
- 围绕工具**直接执行的行为**编写
- 相比技术术语，更从**用户视角**说明

---

### 2️⃣ **When（使用时机/trigger）**

明确说明**在什么情况下应使用此工具**

#### ✅ 好的示例
```
- When: 
  - 用户请求某一主题的信息时
  - 需要最新新闻或趋势信息时
  - 需要事实核查时
```

```
- When:
  - 用户请求模糊或不明确时
  - 收到可作多种解释的问题时
  - 需要额外信息时
```

#### ❌ 不好的示例
```
- When: 需要时（过于模糊）
- When: 总是（不够具体）
```

#### 💡 编写技巧
- 列出**具体情形/条件**
- 用 bullet point 提供多种情况
- 使用"~时", "需要~时"的形式
- 提供判断**何时调用工具**的标准

---

### 3️⃣ **Caution（注意事项）**

明确说明**使用工具时应避免的事项和注意点**

#### ✅ 好的示例
```
- Caution:
  - 搜索 query 要清晰简洁（400 字以内）
  - 优先采用可信来源的信息
  - 没有搜索结果时再次尝试
```

```
- Caution:
  - 不请求用户个人信息
  - 敏感信息加密处理
  - 确认文件大小限制（最大 10MB）
```

#### ❌ 不好的示例
```
- Caution: 小心使用（过于模糊）
- Caution: 不要出错（不够具体）
```

#### 💡 编写技巧
- 列出**具体限制事项**
- 使用"不要~", "注意~", "确认~"的形式
- 明确工具的**局限或限制**
- 包含性能/成本相关注意事项（必要时）
- 包含安全/个人信息相关注意事项（必要时）

## 📊 各工具类型编写示例

### 🔍 搜索工具 (tavily_search, naver_webkr 等)

```markdown
### `tavily_search`
- Purpose: 在互联网上搜索最新信息和新闻
- When:
  - 用户请求某一主题的信息时
  - 需要最新新闻、趋势、事实核查时
  - 回答一般知识问题时
- Caution:
  - 搜索 query 要清晰简洁（400 字以内）
  - 根据需要多次搜索以确认信息
  - 优先采用可信来源的信息
  - 没有搜索结果时换其他关键词重试
```

### 🤔 澄清工具 (ask_clarifying_question)

```markdown
### `ask_clarifying_question`
- Purpose: 通过提问澄清用户的模糊请求
- When:
  - 用户请求存在多种解释时
  - 所需信息不足时
  - 需要准确理解用户意图时
- Caution:
  - 一次只提一个问题（禁止多个问题）
  - 提供 3 个选项和自由输入选项
  - 等待用户回答后再进入下一步
  - 已经明确的请求不要使用
```

### 📁 文件处理工具 (read_agent_file, list_permanent_files)

```markdown
### `read_agent_file`
- Purpose: 读取并处理已上传文件的内容
- When:
  - 用户提出基于文件的问题时
  - 需要查找文档特定部分时
  - 需要分析或总结文件内容时
- Caution:
  - 准确确认文件 ID 后再读取
  - 大文件可能只能读取部分内容
  - PDF 会转换为 Markdown，因此需考虑格式变化
  - 不要将文件内容直接复制到 prompt
```

### 🔧 设置/配置工具 (update_system_prompt, update_model_config)

```markdown
### `update_system_prompt`
- Purpose: 更新 Agent 的完整系统提示词
- When:
  - 首次设置新 Agent 时
  - 需要彻底重写提示词时
  - 没有现有提示词时
- Caution:
  - 不要擅自删除现有指令
  - 工具/中间件变更时一并更新
  - 变更后确认 Agent 行为
  - 局部修改建议使用 edit_system_prompt
```

### 🔄 重复任务工具 (create_cron_schedule)

```markdown
### `create_cron_schedule`
- Purpose: 设置 Agent 的自动执行日程
- When:
  - 需要定期重复执行时（每天、每周等）
  - 需要在特定时间只执行一次时
  - 需要自动化任务时
- Caution:
  - 准确确认 Cron 表达式格式（5 个字段）
  - 确认时区设置（默认值：Asia/Seoul）
  - 最多只能创建 20 个日程
  - 一次性日程应设置为未来时间
```

## 🎨 编写风格指南

### 格式
```markdown
### `工具名`
- Purpose: [说明]
- When: [场景 1], [场景 2], [场景 3]
- Caution: [注意事项 1], [注意事项 2]
```

或者在复杂情况下：
```markdown
### `工具名`
- Purpose: [说明]
- When:
  - [场景 1]
  - [场景 2]
  - [场景 3]
- Caution:
  - [注意事项 1]
  - [注意事项 2]
  - [注意事项 3]
```

### 语言
- 使用自然的韩语编写
- 使用敬语（因为是 Agent 指令）
- 使用命令式语气（"~执行", "~不要执行"）

### 长度
- Purpose: 1-2 句话
- When: 2-4 个条目
- Caution: 2-4 个条目

## ✅ 检查清单

编写 Tool Guidelines 时请确认以下内容：

- [ ] **Purpose**: 是否清楚说明工具做什么？
- [ ] **When**: 是否列出了具体的使用场景？
- [ ] **Caution**: 注意事项是否清晰且实用？
- [ ] **具体性**: 是否没有模糊表述？
- [ ] **工具特性**: 是否反映了工具的特点和限制？
- [ ] **用户视角**: Agent 是否能够理解并遵循？

## 💡 实战技巧

### 1. 先阅读工具文档
- 确认工具的参数、返回值和限制
- 掌握工具的实际功能和局限

### 2. 从 Agent 视角编写
- "Agent 应该在什么时候使用这个工具？"
- "如果错误使用这个工具会怎样？"

### 3. 添加具体示例（可选）
- 对复杂工具可以添加使用示例
- 例："搜索查询示例：'Python 最新版本功能'"

### 4. 明确工具间关系（按需）
- 多个工具配合使用时明确顺序
- 例："先用 list_permanent_files 确认文件，再使用 read_agent_file"
